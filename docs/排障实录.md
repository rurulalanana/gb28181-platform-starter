# 排障实录

记录**已修复**问题的根因、证据与验证方法。目的不是复述改了什么，而是避免下次
再对着同一个现象重新推理一遍 —— 这里每个结论都有抓包或日志做支撑，其中**三次
一开始怪设备，最后证明是平台自己的问题**。

排障顺序建议：先看 §1 的定位方法，再按现象查对应小节。

---

## 1. 定位方法（先立规矩）

### 1.1 不要相信"设备不配合"这个结论

本项目最难的三个问题，第一反应都是"设备有问题"，实际全是平台侧：

| 现象 | 第一反应 | 实际原因 |
|---|---|---|
| 录像检索永远超时 | 设备不支持 RecordInfo | 平台把时间格式写成了 `2026-10-28 10:00:00`，标准要求 `T` 分隔 |
| 进度条拖动无效 | 设备不支持 seek | 平台 INFO 的 From/To tag 反了，设备认为不在对话内，回 200 OK 但忽略 |
| 点播黑屏 | 设备推流慢 | 平台等轨超时设太短，ZLM 永久丢弃视频轨 |

**判定标准**：没有 SIP 报文 / RTP 包 / ZLM 日志三件套之一作为证据，
就不算找到根因。仅凭"试了一下还是不行"改代码，会在错误方向上越走越远
（本项目为此白改过一次 seek，见 §4.2）。

### 1.1.1 SDK 直连设备：返回值不是证据（大华预置位）

国标链路看报文，**SDK 链路看副作用**。大华 SDK 有两条会把人带偏的特性：

1. **`CLIENT_GetLastError` 是线程级"最后一次错误"，成功后不清零**
   调成功的接口后读它，拿到的是上一次失败的残留码。
   只在返回 `false` 之后读才有意义 —— 否则会得出
   「返回 true 但错误码是 0x80000017」这种自相矛盾的结论。

2. **对不支持的指令照样返回 `true`**
   实测某型 IPC：`POINT_SET` / `POINT_MOVE` / `POINT_DEL` 全部返回 true，
   15 秒连续采样 `pan` 恒定不变 —— 云台纹丝不动。

| 现象 | 误判 | 真因 |
|---|---|---|
| 预置位提示「该通道可能无云台」 | 通道号不对 / 无云台 | 通道号是对的（IPC 用 0）；`0x80000015` 是 `NET_RETURN_DATA_ERROR`，在预置点场景表示**该编号没有预置点**，不是型号不支持 |
| 设置预置位「成功」但调用没反应 | 平台没下发 | 该编号原本就不存在；SET 对不存在的编号会假成功 |
| 判定「该型号没有预置点」 | `PtzPreset` 配置项读不到 = 不支持 | **判据用错了**。读清单有三条独立接口，本机只有 `QueryDevState(0x57)` 可用；设备 Web 界面一直有「預置點1」 |

**现在只走设备侧，平台不再存坐标副本**。
早期因为误判「型号不支持」，做过一套「平台存 (pan,tilt,zoom) + 绝对定位回位」的兜底；
后来确认设备完全支持，那套副本已删除 —— 两份数据必然不同步，功能还不如设备侧。

**唯一可信的判据**：
- 能力 → 三条清单接口依次试（`QueryDevState(0x57)` / `GetConfig(1011)` / `PtzPreset` 配置项），
  任一有结果即支持
- 效果 → `NET_DEVSTATE_PTZ_LOCATION` 查到的 `pan/tilt/zoom` 有没有变（`position()`）

**预置点指令的四个必守细节**（错了会被误判成「不支持」）：

| 细节 | 错了会怎样 |
|---|---|
| **预置点号传 `lParam2`**（不是 `lParam1`） | 返回 true，但操作的是「预置点 0」，设备什么都不做 |
| `szReserve` 必须显式清零 | JNA 的 `byte[]` 默认 `null`，设备返回 `0x80000015` |
| 预置点号 **1 基** | 传 0 返回 `0x80000007`（参数不合法） |
| `dwStop` 必须为 **0** | 传 1 同样返回 `0x80000007` |

**参数位置最难发现**。真机对比（用 `QueryDevState(0x57)` 读清单判定）：

```
SET  param1=30 param2=0   → 返回 true，清单里没有 30
SET  param1=0  param2=31  → 返回 true，清单出现 31   ★
GOTO param1=31 param2=0   → 返回 true，位置不变
GOTO param1=0  param2=31  → 返回 true，转到预置点 31 的位置  ★
```

现象是「设置预置点提示成功，设备上什么都没有」，而同一套代码对已存在的编号
看起来也是成功的（其实只是回了原位）—— 极易误判成「型号不支持预置点」。
旁证：SDK Demo 里变倍的速度也传 param2。

**设备侧清单的真机输出**（`QueryDevState(0x57)`）：

```
编号=1  名称=預置點1  坐标=1113,-150,1
```

名称是 **GBK** 编码，按 UTF-8 解会得到 `�A���c1`。

**`0x80000015` 的含义随指令不同**，不要统一翻译成「型号不支持」：
在预置点场景它是「该编号没有预置点」，其它场景可能是参数问题。
`DahuaSdkException` 里对它只给中性描述「返回数据错误」，具体原因由调用方的 hint 说明。

### 1.2 抓包优先级

```bash
# 1) SIP 报文（最有价值，能看清平台发了什么、设备回了什么）
tcpdump -i any -s0 -A 'port 45060' -w /tmp/sip.pcap
tcpdump -i any -s0 -A 'port 45060' | grep -E '^(INVITE|MESSAGE|INFO|SIP/2.0)'

# 2) RTP 是否真的到了
tcpdump -i any -c 200 'udp port 44560'
ss -uanpm | awk '/:44560/ && !/UNCONN/ {f=1} f && /skmem/ {print; f=0}'

# 3) ZLM 内部状态（轨就绪、媒体源、丢包）
grep -E 'emitAllTrackReady|Track not ready|MediaSink' /opt/gb28181/logs/console.log
```

### 1.3 区分"平台日志正常"和"设备收到了"

SIP 是**请求-应答**协议，但"平台没收到应答"≠"设备没收到请求"，也≠"设备拒绝了"。
反过来"设备回了 200 OK"也≠"设备执行了" —— INFO 的 200 OK 只表示收到，不表示生效。
判断必须看**副作用**：设备 OSD 时间有没有跳、会话 `startAt` 有没有变、RTP 有没有断。

## 2. 播放链路

### 2.1 `appendBuffer` 抛 `InvalidStateError`，播放反复中断

**现象**

```
Failed to execute 'appendBuffer' on 'SourceBuffer':
This SourceBuffer has been removed from the parent media source.
```

播放几分钟就断一次，断点位置随机，重连后能继续，但体验极差。

**根因（关键：不是网络问题）**

xgplayer 在 MSE 缓冲不足时会**自己调用内部 `pause()`**（不是用户点的）。
这个 `pause` 被播放器的事件监听捕获，当成用户操作 → 走 `playPause` 逻辑
→ 通过 SIP 发 **PAUSE** 给设备 → 设备停止推流 → ZLM 收不到 RTP，
`general.mediaServer.keepalive` 超时后**销毁媒体源** → 前端 `SourceBuffer`
被移除 → 后续 `appendBuffer` 必然抛 `InvalidStateError`。

**为什么以前只处理了 error code 3**

`_fail` 里只对 code 3（网络错误）做重建，其它错误码直接 `console.warn` 丢弃。
而 `InvalidStateError` 走的是 append 异常，压根没进 error 分支。

**修复**

| 位置 | 改动 |
|---|---|
| `composables/useXgPlayer.js` | 只有 **`p.playPause`**（真实用户入口）才算用户操作，打 600ms 时间窗；窗口外的 `pause` 事件一律忽略 |
| 同上 | 所有 error code 统一走 `_fail` → `scheduleRebuild` |
| `player/WsFlvStream.js` | `_pump` 每轮检查 `media.error` 和 `readyState !== 'open'`，`MAX_APPEND_QUEUE = 256` 防积压 |

**验证方法**

抓 SIP 报文统计 PAUSE 条数：

```bash
grep -c 'PAUSE sip' /tmp/sip.log
```

修复前一次完整播放会打出多条 PAUSE；修复后**整段播放 0 条 PAUSE**。

> 教训：不要覆盖 `p.play` / `p.pause`。播放器内部也调它们，覆盖会把内部调用
> 误判成用户操作。`playPause` 才是 UI 层的唯一真实入口。

### 2.2 点播丢 H264 轨（黑屏、有声音）

**现象**

369 次点播里有 19 次（5.1%）没有画面。日志：

```
MediaSink.cpp: emitAllTrackReady | All track ready use 11818ms
MediaSink.cpp: emitAllTrackReady | Track not ready for a long time, ignored: H264
```

**根因**

ZLM 的 `general.wait_track_ready_ms` 默认 10000ms。实测最慢的一次等轨用了
**11818ms**，超时后 ZLM 把没就绪的视频轨**永久丢弃**，且这个决定绑定在媒体源上
—— 重连不恢复，必须换新的媒体源（重新 INVITE）才有画面。

设备起推慢的根因见 `部署说明.md` §2.1（UDP 收缓冲太小丢掉了 SPS/PPS + 首个 I 帧）。
**两个都要改**：只放大缓冲不改超时，遇到更慢的设备还是会丢；只改超时不放大缓冲，
丢包问题依旧。

**修复**

```yaml
general:
  wait_track_ready_ms: 30000    # 10s → 30s
  unready_frame_cache: 500      # 轨没就绪时先缓存帧，就绪后补发
```

**验证方法**

```bash
grep 'All track ready use' /opt/gb28181/logs/console.log | tail -3
```

期望全部 < 3000ms；偶发 5~8 秒属正常（设备起推慢），只要**没有**
`Track not ready` 就没问题。修复后实测 `All track ready use 8056ms` 仍保留
`H264[1280/720/15]`。

### 2.3 `SIP 事务超时: server=true`（一次 1612 条）

**现象**

```
WARN  SIP 事务超时: server=true [INVITE → sip:34020000001320000001@...]
```

设备收不到 INVITE，点播必然失败。日志量 1612 条。

**根因（jain-sip 的隐藏要求）**

`SipProvider.getNewServerTransaction(request)` 要求 INVITE **必须带 `Contact` 头**，
否则抛 `TransactionUnavailableException`。这个异常在代码里被吞掉了，
结果就是**报文根本没发出去**，然后事务超时。

**修复**

1. `SipMessageFactory.ensureContact()` —— 发 INVITE 前补齐 `Contact`
2. `GbSipListener.send()` —— 建事务失败时退回**无状态** `provider.sendResponse()`，
   保证报文一定发出
3. `InviteResponseRegistry` —— 无状态路径下仍能匹配应答，避免应答丢失

**验证方法**

```bash
grep -c 'SIP 事务超时: server=true' /opt/gb28181/logs/console.log
```

修复后应为 **0**。同时抓包应能看到设备返回 403（设备拒绝但**收到了**，
这是正确行为，说明链路通了）。

### 2.4 进度条拖动无效

**现象**

拖动进度条，设备回 `200 OK`，但画面不跳。

**根因（tag 反了，很隐蔽）**

GB28181 的 seek 是通过 SIP **INFO** 发 `PLAY RTSP/1.0` + `Range: npt=N-`。
INFO 属于对话内请求，`From`/`To` 的 tag 必须与 **INVITE 建立对话时的方向一致**：

- 平台 → 设备：`From` = 平台的 tag，`To` = 设备的 tag
- 代码里写反了 → 设备认为这条 INFO **不属于任何对话** → 回 200 OK 但直接丢弃

`200 OK` 掩盖了问题，所以只看"有没有应答"永远查不出来。

**修复**

`Gb28181SipClient.dialogTagsOf(callId)` 返回 `[fromTag, toTag]`，
`infoRaw()` 与 `ackInvite()` 统一从这里取；`processResponse()` 里
`Gb28181SipClientBridge.onResponse()` 必须**先于** `callback.onRawResponse()` 执行，
否则 tag 还没登记就去匹配应答了。

**验证方法（必须看副作用，不能看应答码）**

1. 拖动前记下画面 OSD 时间，拖动后看 OSD 是否跳到目标时间
2. 会话 `startAt` 时间戳**不应变化**（说明没有重建会话）
3. SIP 报文里只应有 **1 条** INFO

实测：OSD `00:00:17` → `01:00:18`，正好 +3600 秒，会话 `startAt` 未变，INFO 1 条 ✅

## 3. 录像检索

### 3.1 永远 `400 wait for recordinfo timeout[15s]`

**现象**

每次查录像都等满超时（原 15s / 现 20s），设备从不返回目录。

**根因（一个字符）**

GB/T 28181 表 45 要求 `StartTime` / `EndTime` 用 **ISO8601**，日期与时间之间是
**`T`**。平台用了 `2026-10-28 10:00:00`（空格），部分设备直接判定报文非法丢弃。

**修复**

`ManscdpBuilder.isoTime()` 把空格换成 `T`，同时补上设备要求但原实现漏掉的：

```xml
<Secrecy>0</Secrecy>
<Type>all</Type>
```

**验证方法**

```bash
grep 'recordinfo' /opt/gb28181/logs/console.log | tail -5
```

修复前固定 15s 超时；修复后 **553ms ~ 2.2s** 返回 ✅

### 3.2 有录像但列表是空的

**根因（两个独立 bug）**

1. `RecordItem.parseTime()` 用 `indexOf('T')` 判断"是不是时间"，遇到空格格式
   直接判定"不是时间" → `lenient=false` 解析失败 → 返回 null → **整条记录被跳过**
2. `SumNum=0` 时 `accept()` 不认为应答结束（只有 `sumNum > 0` 才收尾），
   一直挂到超时

**修复**

- 解析前先归一化：空格 → `T`
- `sumNum` 用 **`-1` 作"未知"哨兵**（`0` 是合法值，代表真的没有录像）。
  收尾条件：`sumNum == 0 && unique.isEmpty()`

> 教训：**不要用 0 当"未设置"哨兵**。这里 0 有明确业务含义（无录像），
> 用 0 当哨兵会导致"查无录像"时反而挂满超时。

### 3.3 超时次数恰好是成功次数的两倍

**现象**

统计 99 次查询：66 次超时，33 次成功 —— **正好 2:1**。这个比例本身就是线索。

**根因（并发踩同一个单槽）**

前端 `onChannelChange` 同时触发了 `search()` 和 `refreshRecState()`，
**同一通道并发发了两次查询**。而 SIP 的 pager 消息在设备侧是**每通道一个槽位**，
第二次查询的回调覆盖了第一次 → 第一个请求永远等不到应答。

**修复（三层，缺一不可）**

| 层 | 措施 |
|---|---|
| 前端 | 串行化：前一个查询没结束不发下一个 |
| 后端 | 每通道一把锁 + `recordInFlight` 在途去重（相同查询直接复用） |
| 后端 | `recordCache` 15 秒 TTL / 最多 200 条 |

**验证方法**

超时次数应降到接近 0，且 `timeout : success` 不再呈现整数倍关系。

### 3.4 "设备未应答"被显示成"当日无录像"

**现象**

用户以为设备上确实没录像，实际是设备根本没回话。

**根因**

两者在数据层都是**空列表**，接口没有区分语义。

**修复**

API 增加三个字段，前端据此显示不同文案：

| 字段 | 含义 |
|---|---|
| `deviceAnswered` | 设备是否应答（`false` = 未应答，不是没录像） |
| `fromCache` | 结果是否来自缓存 |
| `notice` | 给用户看的提示文案 |

> 原则：**宁可显示"设备未应答"，也不要显示"无录像"**。前者用户知道要重试，
> 后者用户会去设备上找一段根本不存在的录像。

## 4. 走过的弯路（防止重犯）

### 4.1 以为 seek 只能"停流重开"

在 tag 问题（§2.4）修好之前，试过 SIP INFO seek 无效，于是得出"设备不支持 seek"
的结论，改成 `stop + 重新 INVITE` 到目标时间点。

后果：每次拖动进度条都会断流、重新协商、重新等轨 —— 体验极差，用户直接反馈
"为什么是结束推流再开始推流"。

后来对照 **WVP-GB28181-pro** 的实现（`playSeekCmd`）发现它用的正是：

```
PLAY RTSP/1.0
CSeq: N
Range: npt=<秒>-
Content-Type: application/MANRTSP
```

与我们的写法**完全一致**，包括 `Content-Type`。说明 INFO seek 本来就能用，
之前失败纯粹是 tag 反了。

**结论**：`PlaybackView.vue` 的 `seekTo()` 改回 `control({command:'seek', range})`，
仅在失败时才回退 `restartAt()`。`Gb28181MediaService.playbackControl()` 生成上述报文。

> 教训：**在根因未定位前做出的"能力缺失"结论不可信**。先修已知 bug，再重新评估
> 能力边界，否则会把 bug 当成需求限制写进架构。

### 4.2 重复实现了三次"根据任意标识找会话"

`/stream/info` 用它自己的 `streamId` 查不到会话（404），因为三个控制器各写了一份
查找逻辑，都只认 `channelId` 和流名，漏了 `sessionKey`。

修复：统一到 `StreamService.findSession(String)`，按 `sessionKey → channelId → 流名`
依次尝试，三处重复实现删除（净减 101 行）。

> 教训：同一个查询逻辑出现在第二个地方时就应该抽出来，第三个出现时已经晚了。

## 5. 前端布局（三轮才定稿，记下测量值）

### 5.1 播放器下方大空白

三个**独立**原因叠加，所以每修一个都还有残留：

| 轮次 | 原因 | 测量 |
|---|---|---|
| 1 | 视频容器 `height: 74vh` 与实际视频比例不匹配，产生 174px 幻影空间 | — |
| 2 | `contain: size` + `overflow-y: auto` 让容器恒定出现滚动条 | — |
| 3 | 右侧 `PtzPanel` 固定 641px 高，而视频只有 474px，行高由高的一侧决定 | — |

**最终方案**

- 行高由**右列**决定，视频在黑色舞台上居中（`align-items: center`）
- 预览弹窗宽度 `1280px → min(1520px, 96vw)`
- 弹窗内预置位表格 `248px → 176px`
- 右列 `max-height: calc(100vh - 150px)`，仅对矮视口生效

**实测黑边**：167px → **38px** @1440×900，**0** @1920×1080 ✅

### 5.2 切换云台标签页导致高度跳动

提示行用 `v-if` 控制显隐，两个 tab 的内容高度也不同。

修复：提示行改成**等高占位**（`preset-hint-placeholder`），
`.ptz-tabs :deep(.el-tabs__content) { min-height: 252px }`。

**验证**：切换 tab 时高度恒定 **607px**。

### 5.3 状态徽标挤占右列 65px

"播放中 / 缓冲中"原来放在右列顶部，占掉 65px 高度。

修复：移进 `.video-box` 作为覆盖层（左上角），`pointer-events: none` 避免挡点击。

**验证**：`offsetFromVideo {top:10, left:10}`，`pointerEvents: none`，
绿点 `rgb(82,212,122)`，琥珀色 `rgb(240,182,74)` + 脉冲动画。

## 6. 安全与稳定性

### 6.1 公网扫描器污染设备表

**现象**

设备列表里出现 `.`、`0777`、`abc` 这类编号，平台还会主动给它们发 MESSAGE 拉目录，
每次等 32 秒超时，拖慢整体响应。

**根因**

`onRegister` / `onKeepAlive` 接受**任意** deviceId，先入库再去拉目录。

**修复**

## 9. 大华主动注册：设备每 60 秒重连一次

### 现象

```
19:07:40.255 大华设备已注销注册: sn=10001
19:07:40.472 大华设备主动注册: sn=10001 ip=192.168.10.156:56624   ← 源端口每次都变
19:08:40.259 大华设备已注销注册: sn=10001
19:08:40.560 大华设备主动注册: sn=10001 ip=192.168.10.156:56650
```

间隔精确到 **60.004 秒**，设备本身完全正常、平台功能也不受影响。

### 误判（第一次就是这么想的）

「设备主动注册的心跳间隔是 60 秒，它自己会重连，正常现象。」—— 错。

### 真因：平台从不在那条连接上登录

`CLIENT_ListenServer` 的注册回调只是**把一条 TCP 连接交给你**，真正的「确认」是
平台在这条连接上按 `emSpecCap=2 + SN` 登录。不登录时连接停在 SDK 的
**「待验证」** 状态，60 秒超时后被丢弃 —— 设备随即换源端口重连。

`EM_LISTEN_TYPE.NET_DVR_DISCONNECT` 的常量注释写得就是
「**验证**期间设备断线回调」（`-1`），**不是**「设备下线」。
所以回调里既不能当注销处理，也不能据此删注册表记录。

### 证据（2026-11，IPC 10001，fw 3.201）

| 场景 | 观察结果 |
|---|---|
| 平台只记 IP、不登录 | 每 60.004 秒断开 + 换源端口重连，持续 |
| 在注册那条连接上登录 | 连续 **152 秒**只注册 1 次，零断线 |

登录用回调给的 **源端口**（如 `56994`）就成功，说明「回调端口不能当连接目标」这个
旧结论是错的 —— 端口之所以每次都变，正是因为没登录。

### 官方写法（`AutoRegisterConsole.ServiceCB` + 手册 §3.2.4）

```java
case EM_LISTEN_TYPE.NET_DVR_SERIAL_RETURN: {
    new SwingWorker<LLong, String>() {                 // 手册：必须另开线程，否则崩溃
        protected LLong doInBackground() { return login(deviceTreeNode); }
    }.execute();
}
case EM_LISTEN_TYPE.NET_DVR_DISCONNECT: { /* demo 里空实现，只 break */ }
```

### 本平台的实现

- `DahuaRegisterListener.Handler`：注册成功后在**单线程派发器**上回调上层（不在原生线程登录）
- `DahuaConfiguration.serverLoginHandler`：用 `default-username/password` 在 `ip:port` 上
  `ConnectMode.SERVER` 登录。没配密码时返回 `null`（不能瞎试，大华账号连错会锁）
- `NET_DVR_DISCONNECT`：只打 DEBUG，**不删注册表记录**（离线判定交给 `expire-seconds`）
- `DahuaRegisterTable`：「地址变更」只在 **IP** 变了时打 INFO；只有端口变 = 重新建连，打 DEBUG

> 建档用的 `sdk-port`（37777）与登录用的源端口是两个用途，不要互相替换：
> 前者是设备常驻服务端口（换网后仍有效，直连/RTSP 都靠它），
> 后者只在本次注册有效，但只有它能「消费」那条注册连接。

## 10. 报警列表里全是假警情（事件码映射整张都是错的）

### 现象

报警列表里出现 `人脸检测 3665 条`、`图像翻转`、`门禁开门`、`远程登录 12649` 这类条目，
设备明明一切正常；云台一动就多一条「人脸检测」。

### 误判

先怀疑设备乱报警。**不是。设备报得没错，是平台把码译错了。**

### 真因：映射表抄了网上的老式 DVR 对照表

把每个码拿去官方 SDK 源码里反查（`com/netsdk/lib/*.java`，常量带中文注释），
发现**几乎全对不上**：

| 平台原来显示 | 码 | SDK 真实常量 | 真实含义 |
|---|---|---|---|
| 人脸检测 | `0x2123` | `NET_PTZ_LOCATION_EX` | **云台位置上报** |
| 图像翻转 | `0x300C` | `NET_START_LISTEN_FINISH_EVENT` | **订阅完成通知** |
| 区域入侵 | `0x211F` | `NET_ALARM_3GFLOW_EXCEED` | 3G 流量超限 |
| 视频丢失 | `0x2101` | `NET_ALARM_ALARM_EX` | 外部报警输入 |
| 视频遮挡 | `0x2102` | `NET_MOTION_ALARM_EX` | 动态检测 |
| 动态检测 | `0x2103` | `NET_VIDEOLOST_ALARM_EX` | 视频丢失 |
| 视频恢复 | `0x2104` | `NET_SHELTER_ALARM_EX` | 视频遮挡 |
| 视频信号恢复 | `0x2107` | `NET_DISKERROR_ALARM_EX` | 硬盘错误 |
| 门禁开门 | `0x2183` | `SDK_ALARM_NO_DISK` | 无硬盘 |

### 第二个假报警来源：订阅瞬间的「体检报告」

`CLIENT_StartListenEx` 成功时，设备会把**当前全部报警状态整份推回来**。
一台工作正常的球机立刻上送 6 条 `_EX` 事件，结构体首字段 `dwState` **全是 0**，
语义是「这些报警都已结束」—— 也就是「我一切正常」。
不判这个 0，就把体检报告存成了 6 条新报警（现象：一重启就报视频丢失+遮挡+硬盘错误）。

### 第三个：`0x3169` —— 官方没定义，只能靠实测定性

SDK 3.061 的整套 Java 源码 + 5 份官方 PDF **都搜不到 12649**，没有名字可给。
用「dump 结构体 + 对齐时间」认出来的：

| 证据 | 结果 |
|---|---|
| 结构体 | 100 字节，首字段 `dwSize=100` == 实际长度（布局没读错） |
| 字段 | `dwSize, nAction=0, nSequence=3, NET_TIME, 尾部 64 字节 "lte0"` |
| 载荷时间 vs 接收时间 | `14:53:11`(UTC) vs `22:53:15 +08:00`(=14:53:15 UTC) → **就是当下** |
| 对照 `0x2183` | 载荷 `17:07:49` 比接收早 1 小时 → 那是**历史状态回放** |
| 触发条件 | 只在订阅时出现；连续 2 小时操作云台/读配置都不来；登录设备 Web 后台也不来 |

→ 连接/订阅侧的回执，与 `0x300C` 同类。归入 `NOT_ALARM`，**不落库**，日志保留 INFO 可追溯。

> ⚠️ 别给未定义码编中文名。上一版映射表全错，正是因为拿「别的 SDK 版本的 0x31xx 表」套。

### 手法（下次遇到未定义码照这个走）

1. `Get-ChildItem -Recurse -Filter *.java | Select-String 'int NET_ALARM_XXX ='`
   —— PS 5.1 的 `Select-String` **没有** `-Recurse`
2. 回调里 dump 结构体前 128 字节 hex + 可打印 ASCII（字符串字段常在后面）
3. **`dwSize` == `bufLen`** 是「布局读对了」的硬证据
4. 载荷里的 `NET_TIME` 与接收时间对比：等于当下 = 状态回执；早很多 = 历史回放
5. 设备报的是 **UTC**，本地 +08:00 要减 8 小时

## 11. NAT 后的大华设备播不出来：从「SDK 也救不了」到「自己解 DHAV」

### 现象

设备主动注册成功、平台也纳管了、通道同步出来 `10001-1` 且 `ON`，
但一点播就出不来。日志里 ZLM 反复重试：

```
重试播放[0]: rtsp://admin:***@111.198.60.180:554/cam/realmonitor?channel=1&subtype=0
重试播放[1]: ...
```

### 第一层：RTSP 反向连不上（环境原因）

平台原来的大华预览是「ZLM 反向拉设备 RTSP」，方向是**平台 → 设备**；
而主动注册是**设备 → 平台**。设备在 NAT 后时前者被阻断、后者畅通。

实测从服务器出发：

| 目标 | 结果 |
|---|---|
| `111.198.60.180:554`（RTSP） | 连不上 |
| `111.198.60.180:37777`（SDK） | 连不上 |
| `111.198.60.180:80`（Web） | 连不上 |

**这就是「本地一切正常、部署就播不出来」的根因** ——
本地平台与设备同一局域网，RTSP 直连当然通。

> 区分清楚：控制指令（云台/目录/报警）**是通的**，因为复用了设备主动连出来的
> 那条注册会话（见 §9）。只有播放走反向连接。

### 第二层：SDK 取流在这条会话上不给裸流

改成 SDK 取流（`CLIENT_RealPlayByDataType`）后仍然出不了图。
把三种 `emDataType` 全试了一遍，实测结论：

| `emDataType` | Windows 本地 | Linux 服务器 |
|---|---|---|
| `PRIVATE` | DHAV | DHAV |
| `H264` | DHAV + 裸流（`dwDataType=1004`） | **只有 DHAV** |
| `GBPS` | DHAV + 国标 PS（`dwDataType=1001`） | **只有 DHAV** |

**根因：Linux 包漏了 `libStreamConvertor.so`。**

`libdhnetsdk.so` 是用 `dlopen` 加载转封装库的，Java 侧一个符号都不引用：

```bash
strings libdhnetsdk.so | grep '\.so'
# → libStreamConvertor.so / libavnetsdk.so / libplay.so ...
```

而 `sdk-dahua/lib/linux64/` 早期按「Java API 有没有引用」裁剪，把它当无用库删了。
**Windows 官方包没有独立的 `StreamConvertor.dll`（转封装内置在 `dhnetsdk.dll` 内），
所以这个坑只在 Linux 暴露** —— 这正是「本地一切正常、部署就播不出来」的来源。

`dlopen` 失败**不报错**：`CLIENT_RealPlayByDataType` 照常返回句柄，只是
`emDataType` 被静默忽略，回调里只剩私有 DHAV。

> 修法：补回 `libStreamConvertor.so`（27.95 MB），并在
> `src/main/resources/dynamic-lib-load.xml` 里加上 `<lib>StreamConvertor</lib>`
> —— 那份清单是 `LibraryLoad` 的**白名单**，文件放进目录但不写进清单等于没打进去。
> 详见 `sdk-dahua/docs/原生库打包.md` §2.1。

### 这一层排查中走过的三条错路（都值得记住）

1. **「一定是主动注册会话不支持转封装」** —— 错。同版本 SDK、同样
   `emSpecCap=2` + `pCapParam=SN` 注册登录的参考项目在公网服务器上是能拿到裸流的。
   会话类型不是变量，原生库才是。
2. **「设备在 NAT 后，SDK 转封装需要反向连设备」** —— 也错。曾据此写了一版
   「取决于设备可达性」的结论，被用户一句「那个项目也是部署到公网」直接推翻。
   **能反证你结论的证据，往往就在另一个同类项目里。**
3. **「JNA 版本 5.13 vs 5.19 导致结构体没写进 native」** —— 错。本地能拿到 `1004`
   就说明 `emDataType` 写入正常；而且两个 SDK jar 里的
   `NET_IN_REALPLAY_BY_DATA_TYPE` 字段顺序、构造器（都自动填 `dwSize = size()`）
   逐字节一致。

**下次判据**：Java 代码相同、SDK 版本相同、参数相同，只有平台不同时，
**先比两个平台的 `lib/` 目录内容**，不要先怀疑会话类型或 JNA 版本。

中间走过一个坑：把 DHAV 不加过滤直接打 RTP 灌国标收流端口，
ZLM 的日志极具误导性：

```
GB28181Process.cpp:198 onRtpDecode | 08718F60 judged to be PS      ← 它认了
RtpProcess.cpp:234 onDetach | 2(RtpProcess timeout)                ← 15 秒后超时
```

`judged to be PS` 只说明首字节像 PS，**不代表能解出轨道**。
每 18 秒一轮「推流器断开 → 重新放行」，永远建不出轨道。

### 第三层：自己把 DHAV 拆成 Annex-B（这才是解法）

实测 DHAV 帧布局（2026-11，IPC fw 3.201）：

```
0~3    "DHAV"
4      帧类型：0xFD=I 帧 / 0xFC=P 帧 / 0xF0、0xF1=音频或信息帧
12~15  本帧长度（小端，恒等于 dwBufSize，可作完整性校验）
16~39  帧头其余部分
40~    Annex-B 裸流（SPS/PPS/VPS + 切片）
```

探测连续 20+ 个视频帧，首个起始码**全部落在偏移 40**；
音频/信息帧整帧内找不到起始码。

所以判据不用枚举类型字节，而是「帧头之后能否找到 `00 00 01` / `00 00 00 01`」
—— 换固件时帧头长度可能变，但「能解出 NAL 就说明位置对了」这条不会失效。

拆出来的裸流直接交给 ZLM 的 `mk_media_input_h264/265`（`EsMediaPublisher`），
不经过 PS、不经过 RTP，下游 FLV/HLS/WebRTC/RTSP 与国标设备完全一致。

### 顺带修掉的三个「看不见的流」

SDK 流**没有 RtpSession**，而好几处逻辑只遍历会话：

| 问题 | 表现 | 修法 |
|---|---|---|
| `/stream/list` 只遍历会话 | 「当前推流」永远 0 | 补上库里未关闭的直播记录，按 streamKey 去重 |
| `/stream/info` 只查会话 | 永远报「直播流不存在」，前端轮询全失败 | 找不到会话时回落到库记录 |
| `reapIdleStreams` 只扫会话 | 用户关页面后设备一直被取流 | `DahuaSdkStreamService` 自己的 20 秒巡检 |

### 最终验收（服务器，设备在 NAT 后，只有注册会话）

```
ZLM 视频轨道已就绪: 10001/10001-1 codec=H265
ZLM 首帧已推送: 81898 字节 codec=H265
/stream/list  → 10001/10001-1 state=ONLINE transport=SDK
FLV 拉流 733KB / 6 秒，HLS m3u8 HTTP 200
```

浏览器端（`/live` 点通道上屏）也验过，`<video>` 元素 `readyState=4`、
`videoWidth=1280`、`videoHeight=720`、`paused=false`、`error=null`，
画面是设备实景。

**注意前端有两个坑**（自动化测试时会踩，人工点不会）：

- 通道按钮带持续动画，Playwright 的 `click()` 会卡在 `waiting for element to be stable`，
  要 `dispatchEvent(new MouseEvent('click', {bubbles:true}))` 才能触发；
- 页面上 `webrtc://` 那条 `ERR_UNKNOWN_URL_SCHEME` 是 WebRTC 协商失败的兜底尝试，
  **不影响 FLV 播放**，别当成播放失败的证据。

### 通用教训

**「本地正常、线上不正常」先比网络方向，再比代码。**
这轮暴露的五个问题里只有两个是真 bug，其余都是环境差异：

1. `DahuaRegisterTable` 条件 bean —— 本地永远带 `server-mode.enabled=true`（真 bug）；
2. jar 里只有 win64 原生库 —— Windows 打包给 Linux 用（真 bug）；
3. RTSP 反向连不上 —— 本地同局域网，线上 NAT；
4. **Linux 包漏了 `libStreamConvertor.so`** —— `emDataType` 静默失效（真 bug，
   且同样是「两个平台的原生库不一样」，与第 2 条同类）；
5. FLV 用 range 头测不到 —— 我的测试方法错，不代表流有问题。

**部署前必做三件事**（每条都只要几分钟，能挡掉上面大半问题）：

```powershell
# 1. 原生库平台对不对
unzip -l target\*.jar | Select-String 'BOOT-INF/lib/sdk-dahua'   # 解内层看 linux64/

# 2. 本地启动参数是不是「只在本地说得通」—— 逐个删掉 --xxx=true 试启动

# 3. 服务器 → 设备 的端口通不通（决定能不能走反向拉流）
ssh <server> 'timeout 5 bash -c "cat </dev/null >/dev/tcp/<设备IP>/554"'
```

第 3 条如果不通，就说明这台设备**只能走设备主动方向**
（国标推流 / 主动注册），任何「平台去拉设备」的方案都注定失败。

## 二、报警与订阅 ★ 最大缺口

| 能力 | 状态 | 说明 |
|---|---|---|
| 报警信息处理 | ✅ | `AlarmService` 落库 + 去重 |
| **报警推前端** | ❌ | **无 WebSocket**。前端只能手动刷新或轮询，做不到「实时弹窗」 |
| 语音对讲 | ⚠️ | 只有单向喊话（`BroadcastService`），**不是双向对讲**。ZLM C API 无 `startSendRtpTalk` |
| 业务分组/行政区划树自定义展示 | ⚠️ | 字段（`business_group_id` / `civil_code`）已落库，**无树形展示、无自定义** |
| 业务分组级联推送 | ❌ | 目录推送只推平铺通道，不带分组层级 |
| **订阅与通知（框架）** | ❌ | **`SUBSCRIBE` 一次都没发过**。见下方详述 |
| 移动位置订阅 | ❌ | `ManscdpBuilder.mobilePositionSubscribe` 有构造器，**但无人调用** |
| 移动位置通知处理 | ⚠️ | `savePosition` 处理逻辑在，但**不订阅就不会有通知来** |
| 报警事件订阅 | ❌ | `alarmSubscribe` 构造器有，**无人调用** |
| 报警事件通知处理 | ⚠️ | 同上 |
| 设备目录订阅 | ❌ | **无此构造器** |
| 设备目录通知处理 | ⚠️ | `onManscdpRequest` 的 Notify 分支在，但设备不会主动推 |
| 移动位置查询和显示 | ✅ | `PositionLogVo` + `gb_position_log` |
| **报警自动快照 + 播放录像** | ❌ | 报警落库时**不会**自动抓图，也不关联录像 |

### 为什么“订阅”是最大缺口

`Gb28181SipClient` 里**没有任何 `subscribe` 方法**，`subscribeMobilePosition` /
`alarmSubscribe` 这两个 `ManscdpBuilder` 构造器从来没被调用过。
后果：

- 设备**永远不会主动推**报警、位置、目录变更
- 报警只能靠设备发 `Notify`（少数设备会），或者平台主动查
- 目录变更只能靠定时重新查询（现在的做法）
- **`gb_device.alarm_subscribe` / `mobile_position_subscribe` 字段是纯装饰**

这和之前修的 `onManscdpResponse` 死代码是同一类问题：**接口留了、字段存了、通路没接**。

## 七、按优先级排的补齐建议

### P0 — 影响可用性 / 客户会立刻发现（建议先做）

| # | 缺口 | 为什么是 P0 | 工作量 |
|---|---|---|---|
| 1 | **订阅与通知框架（SUBSCRIBE）** | 报警/位置/目录三块全靠它，现在全是死的。一次做完三项收益 | 中（sip 层加 `subscribe`，业务层加订阅表 + 续订任务） |
| 2 | **跨域配置** | 前后端分离部署直接不可用；现成方案 5 行代码 | 极小 |
| 3 | **过滤音频** | 现场噪点设备很常见；ZLM 有 `addDenyAudio` 或流参数可做 | 小 |
| 4 | **报警推前端（WebSocket）** | 「实时报警」是招标硬指标；只有落库没有推送等于没有 | 小（一个 `@ServerEndpoint` + 前端 EventSource） |
| 5 | **国标校时** | 设备时钟漂移会让录像检索全线对不上，排查成本极高 | 小（`DeviceControl` + `Time` 字段，已有构造器基础） |

### P1 — 商业竞争力（有明确需求但不阻塞交付）

| # | 缺口 | 说明 | 工作量 |
|---|---|---|---|
| 6 | 手动添加设备 + 单独密码 | 现场需要预置设备清单，不能全靠自动注册 | 小 |
| 7 | 报警自动快照 + 关联录像 | 招标常见要求「报警时自动抓图」 | 小（已有 `SnapCaptureService`） |
| 8 | 级联虚拟目录 | 上级要按自己的组织架构看通道 | 中 |
| 9 | 双向语音对讲 | 当前只有单向喊话 | 大（ZLM C API 限制，可能需要换方案） |
| 10 | 业务分组/行政区划树展示 | 字段齐了，差前端树 + 级联推送 | 中 |
| 11 | war 打包 | 部分客户只能部署 war 到 Tomcat | 小 |
| 12 | 级联平台状态/信息查询 | 上级调我们时我们要能应答 | 小 |

### P2 — 架构能力（大改，按需启动）

| # | 缺口 | 说明 |
|---|---|---|
| 13 | 流媒体节点集群 | 单 ZLM 是天花板；需要会话路由 + 节点注册 |
| 14 | ZLM 独立部署 | 嵌入式改分布式 |
| 15 | 国标信令集群 | jain-sip 进程级单例，需要外置注册表 + 会话同步 |
| 16 | 拉流/推流 RTSP/RTMP | 非国标设备接入；ZLM 有 `addStreamProxy` 能力 |
| 17 | 多数据库（MySQL/金仓） | schema.sql 需重写 + 方言适配 |
| 18 | 部标 808/1078 | 完全独立协议栈，等于再做一个模块 |
| 19 | 电子地图 | 需要地图引擎 + 瓦片服务 |
| 20 | 虚拟线程 | Java 21 特性；当前 Java 17 用不上 |

## 八、一句话结论

**已覆盖约 75% 的清单**，且核心链路（接入/预览/云台/录像/级联/录像下载）
都是**跑通并经过真机验证**的，不是「有接口没实现」。

**真正的风险集中在两处**：

1. **订阅与通知完全没接**（P0-1）—— 涉及 6 个清单项，且当前字段是装饰性的，
   客户一测就发现「订阅了但收不到」。这是最该优先补的。
2. **部署形态单一**（跨域缺失、只有 jar、只有 PG）—— 不影响功能演示，
   但会在实际交付部署时卡住。

反过来说，WVP 清单里**最重的几项我们反而是超配的**：
嵌入式 ZLM（免配置）、真机验证的级联、S3 对象存储、
录像下载走「回放+录制」而不是依赖设备支持度极差的 `s=Download`。

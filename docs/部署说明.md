# 部署说明

面向单机部署（Spring Boot + 内嵌 ZLMediaKit + PostgreSQL），以现行的
`160.202.254.65` 环境为基准。**第 2 节的内核参数是必做项**，漏掉会直接导致
「重启后第一次播放黑屏」。

## 1. 服务器要求

| 项 | 最低 | 推荐 | 说明 |
|---|---|---|---|
| CPU | 2 核 | 4 核 | 内嵌 ZLM 做 PS 解封装 + 转 FLV/HLS，是 CPU 大户 |
| 内存 | 4 GB | 8 GB | JVM 堆给 1 GB（见 `gb.sh` 的 `-Xmx1024m`），其余留给 ZLM 原生堆与页缓存 |
| 磁盘 | 30 GB | 100 GB+ | 录像约 8 GB/天/通道（1080p 持续录制），靠 `record.disk-max-used-percent` 兜底清理 |
| 系统 | Linux x86_64 | — | zlm4j 原生库支持 win/linux/mac（x86_64 与 arm64） |
| JDK | 21 | — | `JAVA_HOME` 必须指向 JDK 而非 JRE（启动脚本用到 `java`） |

> 磁盘水位要留余量：录像、日志、HLS 切片、PostgreSQL 通常都在根分区。
> 根分区写满后 ZLM 分片写入失败、PostgreSQL 也可能写失败，整个平台瘫痪。

## 2. 系统层前置（必做）

### 2.1 放大 UDP 接收缓冲

```bash
# 立即生效
sysctl -w net.core.rmem_max=16777216
sysctl -w net.core.rmem_default=1048576

# 持久化（重启后仍然生效）
cat > /etc/sysctl.d/99-gb28181-rtp.conf <<'EOF'
net.core.rmem_max = 16777216
net.core.rmem_default = 1048576
EOF
sysctl -p /etc/sysctl.d/99-gb28181-rtp.conf

# 验证
sysctl -n net.core.rmem_max   # 期望 16777216
```

#### 为什么必须做

国标摄像机的编码器**不会平滑发送**：收到 INVITE 后会把攒着的码流一次性倾出，
实测首秒包量约为稳态的 **2.4 倍**。Linux 默认 `net.core.rmem_max` 只有
`212992`（208 KB），一波突发就溢出，内核直接丢包。

**丢的往往是开头的包 —— 而那正好是 SPS/PPS + 首个 I 帧。** ZLM 等各条轨就绪
有时间上限，超时后会把没就绪的视频轨**永久丢弃**：

```
MediaSink.cpp: emitAllTrackReady | All track ready use 11290ms
MediaSink.cpp: emitAllTrackReady | Track not ready for a long time, ignored: H264
```

这个决定是**一次性、绑定在媒体源上**的，媒体源从此只剩音频 → 浏览器永远黑屏。
现场表现是 **「服务重启后第一次播放不出画面，关掉重播就好了」**（重播会生成
新的媒体源，此时突发已经过去）。

#### 验证是否生效

```bash
# 1) 内核层面：RcvbufErrors 应停止增长（它和 InErrors 同步增长 = 收缓冲在溢出）
grep -E '^Udp:' /proc/net/snmp

# 2) 进程层面：承载 RTP 的那个 socket 的 rb 应达到 16 MB 量级
#    注意只看 ESTAB（真正收流的连接），不要看 UNCONN（监听 socket）——
#    单端口模式下 ZLM 为每个设备源各建一个已连接 socket，监听 socket 不承载 RTP。
ss -uanpm | awk '/:44560/ && !/UNCONN/ {f=1} f && /skmem/ {print; f=0}'
#    期望 rb16777216（配置 8 MB，内核按 SO_RCVBUF 记账规则显示为 2 倍，属正常）

# 3) 应用层面：重启后第一次点播，日志里不该出现下面两种行
grep -E 'Track not ready|Cached frame of unready track' /opt/gb28181/logs/console.log
grep 'All track ready use' /opt/gb28181/logs/console.log | tail -1
#    期望 < 3000ms。偶发 5~8 秒是设备起推慢，只要没有 Track not ready 就没问题。
```

### 2.2 日志与文件句柄

日志由 `gb.sh` 在启动时轮转（`LOG_MAX_MB` 默认 100、`LOG_KEEP` 默认 5），
一般无需额外配置。若通道数很多（>50），建议：

```bash
cat >> /etc/security/limits.conf <<'EOF'
*  soft  nofile  65535
*  hard  nofile  65535
EOF
```

## 3. 端口与防火墙

以 `application-server.yml`（`--spring.profiles.active=server`）为例：

| 用途 | 端口 | 协议 | 是否需对外 |
|---|---|---|---|
| Spring Boot HTTP（前端 + REST） | 48088 | TCP | ✅ 用户访问 |
| ZLM HTTP（HTTP-FLV / HLS / WS-FLV） | 48089 | TCP | ✅ 播放器直连 |
| SIP 信令 | 45060 | **UDP + TCP** | ✅ 设备注册 |
| RTP 收流（单端口模式） | 44560 | **UDP + TCP** | ✅ 设备推流 |
| ZLM RTMP | 41935 | TCP | 可选（推拉流工具） |
| ZLM RTSP | 48554 | TCP | 可选（VLC 验证） |
| ZLM WebRTC | 48000 | UDP + TCP | ✅ 若启用 WebRTC 通路的播放 |

```bash
# firewalld 示例
firewall-cmd --permanent --add-port=48088/tcp
firewall-cmd --permanent --add-port=48089/tcp
firewall-cmd --permanent --add-port=45060/udp --add-port=45060/tcp
firewall-cmd --permanent --add-port=44560/udp --add-port=44560/tcp
firewall-cmd --permanent --add-port=48000/udp --add-port=48000/tcp
firewall-cmd --reload
```

注意事项：

- **SIP 必须同时放行 UDP 与 TCP**：部分设备只走 TCP；`sip-transports` 默认两者都开。
- **`rtp-single-port: true` 时只需放行一个 RTP 端口**；关闭该选项则每通道独占端口，
  端口池受 ZLM 限制（`[30000,35000]`，约 2500 对），防火墙也要放行整段。
- **`media-ip` / `sip-advertised-ip` 必须是设备可达地址**（NAT 后要填公网 IP），
  否则设备会往错误地址推流，表现为「INVITE 成功但 ZLM 一直收不到 RTP」。

## 4. 目录结构

```
/opt/gb28181/
├── gb28181-platform-starter-<版本>.jar   # 应用（内含前端静态资源）
├── gb.sh                                 # 启停脚本（deploy/gb.sh）
├── .env                                  # 数据库密码等敏感项，权限 600
├── record/                               # 云端录像（MP4）
├── www/                                  # HLS 切片根目录（ZLM 自动轮转，体积很小）
└── logs/
    ├── console.log                       # 当前日志
    └── console.log.1 … .5                # 历史轮转
```

**`gb.sh` 不依赖具体版本号**：它按 `gb28181-platform-starter-*.jar` 查找，
自动排除 `-sources` / `-javadoc` / `.bak` / `.new`，命中多个时取修改时间最新的那个。
所以升级时**文件名带什么版本都可以**，不需要改脚本。
特殊场景（如回滚到某个 `.bak`）可以显式指定：

```bash
JAR=/opt/gb28181/gb28181-platform-starter-1.0.0.jar ./gb.sh start
```

`gb.sh` 会从 `.env` 注入环境变量（`set -a; . .env`），因此数据库密码**不要**
写进 `application.yml`（会被打进 jar 并提交到 Git）。

```bash
# /opt/gb28181/.env 示例
GB_DB_URL=jdbc:postgresql://127.0.0.1:5432/gb28181
GB_DB_USERNAME=postgres
GB_DB_PASSWORD=********
chmod 600 /opt/gb28181/.env
```

## 5. 首次部署

```bash
# ---- 服务器侧 ----
mkdir -p /opt/gb28181/{logs,record,www}
cd /opt/gb28181
# 上传 jar 与 gb.sh
chmod +x gb.sh

# 1) 系统前置（第 2 节）
# 2) 建库（表结构由应用启动时自动执行 db/schema.sql，无需手工建表）
#    createdb gb28181  / 或 psql -c "CREATE DATABASE gb28181"

# 3) 配置数据库连接
vim /opt/gb28181/.env

# 4) 启动
./gb.sh start

# 5) 观察
./gb.sh log
#   期望：Started Gb28181PlatformApplication in x.x seconds
#        GB28181 平台已启动：SIP 0.0.0.0:45060 / 媒体 http=48089 …
#        数据库表结构初始化完成：成功 N 条，失败 0 条
```

`gb.sh` 的语义：

| 命令 | 行为 |
|---|---|
| `start` | 用 `setsid` 拉起**守护循环**，脱离 SSH 会话；JVM 退出后 3→10→30→60→120 秒退避重拉 |
| `stop` | 先停守护循环再停 JVM。JVM 因原生库析构会卡住，20 秒后强制 kill，属已知现象 |
| `restart` | `stop` + `start` |
| `status` | 打印 JVM / guard 的 PID、监听端口、运行时长与内存、日志体积 |
| `jar` | 打印**实际在跑的是哪个 jar**（路径 / 大小 / MD5）—— 升级后确认用 |
| `log` | `tail -f logs/console.log` |

> **必须用 `setsid`（`gb.sh` 已内置）**：直接在 SSH 会话里 `nohup java` 启动，
> 会话关闭后进程会被一起杀掉。

## 6. 升级部署

```bash
# ---- 构建机 ----
mvn clean package -Dmaven.test.skip=true -Dgpg.skip=true

# ---- 服务器 ----
cd /opt/gb28181
JAR=$(ls -t gb28181-platform-starter-*.jar | grep -vE 'sources|javadoc|\.bak|\.new' | head -1)
cp "$JAR" "$JAR.bak"

# 上传新包为 .new，再原子替换（传完先比 md5）
md5sum gb28181-platform-starter-*.jar.new
mv -f gb28181-platform-starter-*.jar.new "$JAR"
md5sum "$JAR"                       # 与构建机比对

./gb.sh stop
setsid nohup ./gb.sh start >/tmp/start.log 2>&1 < /dev/null &
sleep 20
./gb.sh status
./gb.sh jar                         # 确认跑的是预期那个 jar
```

升级后必查（各一次即可）：

```bash
L=$(grep -n 'Started Gb28181PlatformApplication' logs/console.log | tail -1 | cut -d: -f1)
tail -n +$L logs/console.log | grep -c ' ERROR '   # 期望 0
```

> **前端已打进 jar**：`npm run build` 输出到 `src/main/resources/static/`，
> 构建物**随仓库提交**。只改前端也要重新 `mvn package` 并走一遍上面的升级流程。

## 7. 验收清单

| # | 操作 | 期望 |
|---|---|---|
| 1 | `sysctl -n net.core.rmem_max` | `16777216` |
| 2 | `./gb.sh status` | JVM 与 guard 都在运行 |
| 3 | 启动日志 | `Started Gb28181PlatformApplication`，ERROR 数 0 |
| 4 | 设备上线 | `设备注册: deviceId=…`、`目录已同步: device=… 通道数=…` |
| 5 | **重启服务后立刻点播** | 画面秒出；无 `Track not ready` 警告；`All track ready use` 通常 < 3 秒 |
| 6 | 四种协议切换 | FLV / HTTP-FLV / WebRTC / HLS 均可播放（HLS 无声音，属规范限制） |
| 7 | `df -h /` | 使用率低于 `record.disk-max-used-percent`（默认 85%） |

第 5 项是这套部署最容易翻车的地方，**每次升级后都要手动验一次**。

## 8. 排障

### 8.1 重启后第一次点播黑屏，关掉重播就正常

**根因**：见 [2.1](#21-放大-udp-接收缓冲)。内核丢掉了开头的 SPS/PPS + 首个 I 帧，
ZLM 把视频轨永久丢弃。

**按序检查**：

```bash
# ① 内核参数是否真的生效
sysctl -n net.core.rmem_max                       # 必须是 16777216

# ② RTP socket 缓冲是否被放大了（只看 ESTAB，不看 UNCONN 监听 socket）
ss -uanpm | awk '/:44560/ && !/UNCONN/ {f=1} f && /skmem/ {print; f=0}'
#    期望 rb16777216

# ③ 日志里是否还有轨被丢弃
grep -E 'Track not ready|Cached frame of unready track' logs/console.log | tail

# ④ 丢包是否仍在持续（稳态 1% 左右属公网正常抖动）
grep -c 'packet dropped' logs/console.log
```

若 ① ② 都正常但仍黑屏，说明是设备侧问题（码流本身无 I 帧、或设备只推子码流），
用 RTSP 直连设备验证：

```bash
ffprobe -v error -show_entries stream=codec_name,width,height -of csv=p=0 \
        rtsp://<设备IP>/<路径>
```

### 8.2 磁盘增长过快

```bash
df -h /
du -sh /opt/gb28181/record/*        # 按通道看占用
```

- 调小 `record.retain-days`（运行时配置，界面可改，立即生效）
- 调低 `record.disk-max-used-percent`（默认 85）
- 检查是否有 `*_playback` / `*_download` 临时目录残留（后台下载用的中转文件，
  不参与数据库对账，不会被自动清理，需手工 `rm -rf`）

### 8.3 设备注册不上

1. `sip-advertised-ip` / `media-ip` 是否为设备可达地址
2. 防火墙是否同时放行 SIP 的 UDP 与 TCP
3. 报「注册认证失败」→ 检查 `sip-password`（系统级统一密码，留空=不鉴权）
4. 报「命中黑名单」→ 检查接入控制配置

### 8.4 JVM 被 SIGABRT 杀掉

日志特征：

```
terminate called after throwing an instance of 'toolkit::AssertFailedException'
  what():  Assertion failed: (ctx && dst_url && ssrc), function mk_media_source_start_send_rtp4
```

已修复（上级 INVITE 的 SDP 不带 `y=` 时不再向原生层传 `ssrc=null`）。
若仍出现，检查是否跑的是旧 jar：`./gb.sh jar` 会打出**实际在跑的 jar 全路径、大小与 MD5**。

## 附录 A：平台自动注入的 ZLM 配置

以下参数由**代码注入**，不需要写 ini，也不要在服务器上单独维护 `config.ini`：

| ZLM 配置项 | 取值 | 注入位置 |
|---|---|---|
| `rtp_proxy.udp_recv_socket_buffer` | `gb28181.udp-recv-socket-buffer`（默认 8 MB） | `ZlmMediaServer#applyProtocolOptions` |
| `protocol.hls_save_path` | `MediaServerProperties.hlsSavePath`（默认 `${user.dir}/www`，即 `/opt/gb28181/www`） | 同上 |
| `http.rootPath` | 同 `hls_save_path`（必须一致，否则 m3u8 能拉、切片 404） | 同上 |
| `hls.segDur` / `segNum` / `segRetain` | 2 / 3 / 5 | 同上 |
| `protocol.mp4_as_player` | `1`（录制计为观看者，避免「只录像没人看」被误关流） | 同上 |
| `general.streamNoneReaderDelayMS` | `gb28181.stream-none-reader-delay-ms`（默认 45000） | 同上 |
| `rtc.externIP` / `rtc.port` | `gb28181.rtc-extern-ip` / `rtc-port` | 同上 |

> **踩过的坑**：`hls_save_path` 属于 `[protocol]` 段，写成 `hls.hls_save_path`
> 时 `mk_set_option` 会静默接受、但没人读 —— 切片落到 `$JAVA_HOME/bin/www`，
> 而 `http.rootPath` 指向别处，表现为 **m3u8 能拉到、每个 `.ts` 都 404**。

# 商用化差距分析（对标 LiveGBS / cms.gxhypro.com）

> 调研方式：实际登录参考站逐页抓取功能点（设备/分屏/云录/报警/级联/用户/日志/配置），
> 同时全量审计本项目三个模块的源码、接口、表结构与前端路由。
> 结论按「上生产会不会出事」排序，不按「做起来爽不爽」排序。

## 0. 一句话结论

**协议与媒体内核是强项，平台层是短板。**
SIP/MANSCDP/SDP 编解码、ZLM 收流、云端录像、ws-flv 播放这条主线做得比多数开源项目扎实
（122 个测试，注释标了国标条款）；但**平台层「面上很全、深度不足」**：
154 个接口里约 1/3 只有下发没有应答闭环，权限只有两档且几乎不设防，
审计记不到「改了什么」，整体是单进程单实例架构。

商用要补的不是功能数量，而是四件事：**权限、审计、数据生命周期、可运维性**。

## 2. P0 阻断项（本轮的修复已完成，逐条列出以便复核）

### 2.1 权限模型不成立 → 已修

**改造前实测**（`grep -c checkRoleOr`）：

```
ConfigController      checkLogin=4   checkRoleOr=0
DeviceController      checkLogin=38  checkRoleOr=0
ControlController     checkLogin=24  checkRoleOr=0
CascadeController     checkLogin=13  checkRoleOr=0
RecordPlanController  checkLogin=6   checkRoleOr=0
StreamController      checkLogin=8   checkRoleOr=0
RecordController      checkLogin=3   checkRoleOr=0
```

任何一个只读账号都能：改「设备统一接入密码」让全平台设备注册失败、
`/system/restart?force=true` 退出 JVM、删设备、建录像计划占满磁盘、改级联、控云台。

**修法**：新增 `WritePermissionInterceptor`，策略反转成**默认拒绝** ——
非 GET 请求一律要求写权限，管理类前缀要求管理员。白名单只留
「登录/登出/改自己密码/查自己信息」+「播放取址（`stream/start`、`webrtc/play`，
只读语义）」。

为什么用拦截器而不是逐接口加注解：19 个类 154 个方法，漏一个就留一个洞，
且**以后新增接口默认仍敞开**。收口后新接口不用记得加注解也不会漏，
加错白名单最坏结果是「功能被挡」而不是「权限泄露」——失败方向是安全的。

三档角色：`admin` 全部 / `operator` 日常运维（设备、云台、录像、报警）/
其它只读。

### 2.2 停用/删除用户不踢下线 → 已修

`UserController.remove/setenable/resetpassword` 原来只改库。
鉴权只校验 `checkLogin()`，**不校验账号是否还存在** ——
被删账号的 token 能继续用到过期（默认 **7 天**）。
「开除一个人、收回了账号，他还能看一周全部录像」是审计必问的问题。
现改为操作后 `StpUtil.logout(userId)`，失败降级为告警日志
（主体操作已成功，不该因为踢人失败而报「操作失败」诱导重试）。

### 2.3 审计记不到「改了什么」→ 已修

三个缺陷叠加，让日志在追责时几乎无用：

1. **不记参数** → 只能确认「动过」，无法确认「改成了多少」；
2. **`result` 取 HTTP 状态码** → 本项目 HTTP 恒为 200，
   于是**业务失败在日志里全是 200**（越权被拒、参数校验失败、服务端异常统统显示成功）；
3. 无 SIP 级审计。

修法：
- `gb_operation_log` 加 `params` 列（1024 字符截断）；
- `OperationLogInterceptor` 在 `preHandle` 采集参数并**脱敏**
  （名字含 `password/secret/token/key/cert/private_key` 一律替换为 `***(N字符)`）——
  审计日志本身不能变成凭据泄漏源，它会被导出、被备份、被拷到本地排查；
- 新增 `ApiResponseAdvice`（`ResponseBodyAdvice`）在响应写出前把
  `code/msg` 挂到请求属性，审计读它拿到**真实业务结果**（含失败原因）。
  用属性传递而不事后解析响应体：响应流已写出，再读会二次消耗。

### 2.4 三张表无限增长 → 已修

`gb_alarm`、`gb_position_log`、`gb_device_record` **此前没有任何清理路径**。
高频点位（移动侦测报警、车载 GPS）几个月就能把库撑到几十 GB，
而这三张表都参与按时间倒序分页 —— 表现是「报警页越来越慢，最后打不开」，
清理只能靠 DBA 手工 DELETE。

新增 `PlatformScheduler.purgeUnboundedTables()`（每小时）+ 三个运行时配置项：

| 配置项 | 默认 | 理由 |
|---|---|---|
| `alarm.retain-days` | 180 | 报警按季度复盘，是该看的都在与库不胀的平衡点 |
| `position.retain-days` | 30 | 增长最快的表；轨迹只用于回溯「最近去过哪」 |
| `device.record-retain-days` | 30 | 只是设备录像检索的**缓存**，真实清单在设备上 |

`gb_device_record` 用 `update_time` 而非 `create_time` 作判据（该表没有 `create_time` 列，
每次重新检索会 upsert 同一批文件并刷新 `update_time`）。

## 3. P0 未修（需要排期，按优先级）

### 3.1 级联到上级平台不可用

无主动 REGISTER/保活，`pushCatalog` 必然失败（见 §1.5）。
这是**功能承诺与实现不符**，验收时会被直接指出。

补法：`CascadeClient` 增加主动注册线程（`REGISTER` + 定时刷新 + 401/403 处理），
`CascadeRegistry` 记录上级会话；`pushCatalog` 改走上级会话而非本地注册表。

### 3.2 单进程单实例，无法高可用

- ZLM 以 `zlm4j` **内嵌在同一 JVM**；jain-sip 进程级单例；
- 大量状态在进程内：会话、转推、录像策略、目录分页、采集节流、指标历史；
- `ShareTokenService` / `RecordUrlSigner` 的 HMAC 密钥是**启动时随机生成** ——
  多实例部署时 A 节点签的 URL 到 B 节点必然 403；重启后已发出的链接立即失效；
- 所有 `@Scheduled` 在多实例下会重复执行；
- ZLM native 崩溃（README 已记录 `SIGABRT`）会带整个平台一起挂。

商用取舍有两条路：**A. 明确「单机版」定位**并把备份/恢复/巡检做扎实；
**B. 拆成「信令+平台」与「媒体」两个可独立扩缩的进程**。以目前架构，A 更现实。

### 3.3 列表接口无数据库分页

`DeviceController.list/channelList`、`AlarmController.list`、`CascadeController.channelList`、
`UserController.list`、`RecordPlanController.channelList` 全是
**`selectList` 全表 + Java 过滤 + Java `subList`**；
`DeviceController.channelView()` 每行查设备+查会话（**N+1**）；
`CloudRecordController.queryChannels` 每个通道各查一次录像（**N+1**）；
`limit=0` 允许一次拉全量且无上限。

千级通道/万级报警时会出秒级到十秒级延迟与内存峰值。
补法：把 `PageQuery` 下沉到 SQL（`limit/offset` + `count`），
N+1 改批量 `IN` 查询，`limit` 设上限（如 500）。

### 3.4 阻塞式接口会耗尽线程与连接池

- `/playback/recordlist` 同步等设备应答，默认 **15 秒**；
- `/cloudrecord/snap/grab` 最长 **35 秒**（25s 等流 + 10.5s 解码），全局并发只有 2；
- Hikari `maximum-pool-size: 10`。

叠加时很容易打满。另外 `Gb28181MediaService.recordCallbacks` 按 **`deviceId` 单键**
保存回调 —— 两个用户同时查同一设备会互相覆盖。

补法：改异步任务 + 轮询/推送结果；并发限制改按用户配额；回调键加请求 ID。

### 3.5 默认部署下录像回放会 404

`application.yml` 默认 `record-static-enabled: false`，但接口仍回填 `/record/...`。
没有 nginx `location /record/` 时播放器直接 404。
只有 `/cloudrecord/file/{id}` 是应用内兜底，而前端优先用 `playUrl`。

补法：启动自检时探测 `/record/` 是否真的可访问，不可访问则告警并
让 `toStaticUrl` 回落到受保护接口。**这是「装完就能用」的关键一环。**

## 4. P1（上线后很快暴露）

1. **假功能/死配置会误导验收**：语音喊话（只发 MANSCDP 不传音频，且注释指向不存在的 ws 接口）、
   设备录像下载（`download=true` 未实现）、转推、解码上墙（状态恒 PENDING）、
   OSD（恒 400）、抓拍配置/升级/目标跟踪（恒 PENDING）、设备分组、预置位名称、
   通道音频/分享、设备状态/配置/预置位/巡航查询（下发无应答解析）。
   **建议：要么补齐闭环，要么从 UI 与文档里移除**。留着比没有更糟。
2. **设备订阅不发 SUBSCRIBE**：报警能力的前提，注册时应当自动订阅
   （按 `*Subscribe` 字段）。
3. **时区**：全项目 `LocalDateTime.now()` + 无时区 `TIMESTAMP`，
   跨时区/容器 UTC 下会出现「报警时间差 8 小时」「录像检索不到」。
4. **外部依赖硬编码**：`FfmpegSnapService.FFMPEG = "/opt/gb28181/bin/ffmpeg"` 写死；
   `TlsCertificateService` 固定 `/etc/nginx/conf.d/` 且要求 root；`/proc` 依赖 Linux。
5. **无部署物**：只有 `gb.sh` + nginx 模板，**无 Dockerfile / systemd / K8s 清单**。
6. **配置与密钥进仓库**：`application.yml` 里有生产 DB 地址与通告 IP，
   `schema.sql` 写死 `admin/admin123`，登录页还印着这行提示。
7. **无迁移框架**：`schema.sql` 是「初始化 + 幂等 ALTER 补丁」，无版本表、无回滚；
   `SchemaInitializer` 失败只 `log.error` 后继续启动。
8. **播放器依赖**：H.265 走 MSE 硬解，Windows 无 HEVC 扩展时黑屏且不转码；
   ZLM 崩溃残留的 MP4（无完整 moov）无法播放。
9. **无并发控制**：设备/通道编辑是「读实体 → 改字段 → `updateById` 全行覆盖」，
   两个管理员同时编辑会丢更新。
10. **可观测性缺失**：无 actuator / Prometheus / OpenAPI / traceId；
    `PlatformAsyncExecutor.rejectedCount()` 有计数器但不暴露。

## 5. 国密 35114

参考站只有一个勾选框。我们没有做「开关」，而是做了**就绪度自检**
（`GET /api/v1/tls/gm-readiness`），实测本机五项前提全缺：

| 前提 | 实测 |
|---|---|
| JDK SM2/SM3/SM4 | ❌ 标准版 JDK 不含 |
| BouncyCastle | ❌ 未引入 |
| OpenSSL SM2 曲线 | ❌ 1.1.1k 只支持 SM3 摘要 |
| nginx 国密套件 | ❌ 1.14.1 标准版不支持 ECC-SM4-SM3 |
| 设备证书 CA | ❌ 无 |

35114 是密码体系而非开关：要 CA 签发设备证书、信令数字签名、
按 A/B/C 三级对视频签名/加密，通常还需国密局认证的密码硬件，
且 ZLM 不做 35114 视频解密。**空开关比没有更糟**——勾上之后每台设备都会注册失败。
分期方案见 `docs/GB35114-评估.md`。

| **一期** | 「装完就能用」 | 部署物（Dockerfile/systemd）、启动自检（录像可访问/ffmpeg/nginx）、配置外置、强制修改默认口令、SQL 分页 |
| **二期** | 「能验收」 | 级联主动注册、设备订阅、报警联动（预案+关联录像/快照）、移除或补齐假功能 |
| **三期** | 「能运营」 | 按通道授权（`gb_user_channel`）、操作员数据范围、可观测性（actuator+Prometheus+OpenAPI）、异步化阻塞接口 |
| **四期** | 「能投标」 | 35114 分期（视招标条款而定）、等保相关整改 |

**不建议做的事**：为了「功能对齐」去堆一堆只有接口没有闭环的功能。
现场演示时的第一句话往往是「点一下我看看」——
留下一个点了没反应的功能，比明确说「这个不支持」伤害大得多。
